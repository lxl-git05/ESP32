# Template 项目库管理说明

本文用于说明项目的文件组织、新增模块方法和头文件引用规则，方便后续扩展及交接。文中的路径均相对于 `Template` 工程目录，不依赖某台电脑的盘符。

**日常添加功能的步骤：创建 `.h` 和 `.c/.cpp` → 声明接口 → 实现函数 → 在调用处包含头文件 → 调用函数 → 编译。**

## 1. 当前结构与职责

```text
Template/
├── Template.ino          主程序：setup()、loop()
├── Initial.h             统一初始化接口，目前也汇总部分头文件
├── Initial.c             实现 Initial_All()，统一安排初始化
├── src/
│   ├── Hardware/         硬件层：引脚配置、器件读写等
│   │   ├── LED.h         LED 对外接口
│   │   └── LED.c         LED 驱动实现
│   └── Wifi_Base/        预留 Wi-Fi 模块目录，目前为空
├── .vscode/              编辑器及开发工具配置
├── build/                编译生成的文件
└── 库管理说明.md
```

目前的初始化关系是：`setup()` 调用 `Initial_All()`，后者调用 `LED_Init()`。`loop()` 调用全局函数 `print_FreeRtos_Task()`，采样约 1 秒后打印全部任务，再阻塞 2 秒；任务监视的用法见第 7 节。

`Hardware`、`Wifi_Base` 等目录用于组织**本工程的模块**，可以继续增加平级目录。跨项目安装到 Sketchbook 的 Arduino 库是另一种管理方式；本文采用工程内管理，不需要为这些目录创建 `library.properties`。

Arduino 会编译工程根目录中的 `.c/.cpp`，并递归编译 `src` 下各级目录中的 `.c/.cpp`。因此新增文件无需登记源文件列表，也无需修改编译搜索路径。需要参与编译的子目录应放在 `src` 下，`.ino` 入口保留在工程根目录。[官方工程规范](https://docs.arduino.cc/arduino-cli/sketch-specification/)

**自动参与编译不等于自动执行。** 模块的初始化和业务函数仍需由主程序或上层模块调用。`src` 中暂时不用的源码也会参与编译，不要把未完成、无法编译的实验代码当作备份留在这里。

## 2. 新增模块的两种情况

以下 `Software`、`Control` 和 `Key` 均为未来扩展示例，当前项目尚未创建。

### 情况一：新增 Software 层

例如，在 `src` 下建立与 `Hardware` 平级的 `Software`，存放控制或业务逻辑：

```text
src/
├── Hardware/
│   ├── LED.c
│   └── LED.h
└── Software/
    ├── Control.c
    └── Control.h
```

1. 创建 `src/Software` 文件夹，再创建 `Control.h`、`Control.c`。
2. 在 `Control.h` 声明 `Control_Init(void)`、`Control_Run(void)` 等对外接口，在 `Control.c` 中实现。
3. `Control.c` 包含自己的 `"Control.h"`；如果使用 LED，再包含 `"../Hardware/LED.h"`。
4. 在 `Initial.c` 中包含 `"src/Software/Control.h"`，并在 `Initial_All()` 中调用 `Control_Init()`。
5. 在 `Template.ino` 中包含 `"src/Software/Control.h"`，在 `loop()` 中调用 `Control_Run()`。
6. 保存全部文件并编译，检查声明、实现和调用是否一致。

硬件操作交给 `Hardware`，业务逻辑由 `Software` 调用硬件接口完成。例如控制层调用 `LED_On()`，不必重复处理 LED 的引脚和有效电平。

### 情况二：在 Hardware 中添加模块

例如新增按键模块，直接和 LED 文件并列，无需再建一层文件夹：

```text
Hardware/
├── LED.c
├── LED.h
├── Key.c
└── Key.h
```

1. 创建 `Key.h`、`Key.c`。
2. 在 `Key.h` 声明按键接口，例如 `Key_Init(void)`、`Key_Read(void)`；在 `Key.c` 中实现，并包含自己的 `"Key.h"`。
3. 如果实现使用 Arduino GPIO 接口，显式包含 `<Arduino.h>`。
4. 在 `Initial.c` 中包含 `"src/Hardware/Key.h"`，并在 `Initial_All()` 中调用 `Key_Init()`。
5. 谁读取按键，谁包含 `Key.h` 并调用读取接口：主程序和控制层的引用路径见下一节。
6. 保存全部文件并编译，再检查实际硬件行为。

如果某个模块没有初始化工作，可以不提供初始化函数，也不必修改 `Initial_All()`。

## 3. 不同位置的文件如何引用

项目内头文件统一使用带双引号的相对路径。**从写下这条 `#include` 的文件所在目录出发，找到目标头文件。** 如果引用写在 `.h` 中，就从该 `.h` 所在目录计算。

| 写入引用的文件 | 要引用的文件 | 写法 |
|---|---|---|
| `Template.ino` | 根目录的 `Initial.h` | `#include "Initial.h"` |
| `Initial.c` 或 `Initial.h` | 硬件层的 `LED.h` | `#include "src/Hardware/LED.h"` |
| `src/Hardware/LED.c` | 同目录的 `LED.h` | `#include "LED.h"` |
| `Template.ino` | 未来的 `Key.h` | `#include "src/Hardware/Key.h"` |
| `Template.ino` | 未来的 `Control.h` | `#include "src/Software/Control.h"` |
| 未来的 `src/Software/Control.c` | 硬件层的 `LED.h` | `#include "../Hardware/LED.h"` |
| 未来的 `src/Software/Control.c` | 硬件层的 `Key.h` | `#include "../Hardware/Key.h"` |
| 未来的 `src/Software/Tasks/Blink.c` | 硬件层的 `LED.h` | `#include "../../Hardware/LED.h"` |

路径中的 `../` 表示向上一级，`../../` 表示向上两级。例如最后一行先从 `Tasks` 返回 `Software`，再返回 `src`，最后进入 `Hardware`。这是未来嵌套目录的写法示例，不要求现在创建 `Tasks`。

- 使用 `/` 分隔路径，保持文件名和大小写完全一致。
- 不要把开发者电脑上的绝对路径写入 `#include`，否则换电脑后容易失效。
- 同目录可直接写文件名；跨目录时按上表写出明确路径，不依赖编辑器的补全结果。
- `<Arduino.h>`、`<WiFi.h>` 等通常来自开发板核心或已安装库，由编译器配置的搜索路径查找。双引号引用首先查找当前文件附近的位置，也可能继续搜索配置路径。
- 只包含 `.h`，不要包含 `.c/.cpp`；源文件会单独编译，再由链接器连接到程序。

## 4. 可复制的 C 模块模板

下面是一组未来 `Software/Control` 的示例。它只演示接口组织和调用 LED，实际业务可以替换函数体。

**Control.h：**

```c
#ifndef TEMPLATE_CONTROL_H
#define TEMPLATE_CONTROL_H

#ifdef __cplusplus
extern "C" {
#endif

void Control_Init(void);
void Control_Run(void);

#ifdef __cplusplus
}
#endif

#endif
```

**Control.c：**

```c
#include "Control.h"
#include "../Hardware/LED.h"

void Control_Init(void)
{
    // 初始化本模块状态；LED 由 Initial_All() 先行初始化。
}

void Control_Run(void)
{
    LED_On();  // 示例：通过硬件层接口点亮 LED。
}
```

复制为其他模块时，修改头文件保护名、函数名前缀及所需引用。每个头文件的保护名必须不同，例如 `TEMPLATE_KEY_H`；否则可能导致另一个头文件的内容被意外跳过。

`.ino` 按 C++ 编译，`.c` 按 C 编译。模板中的 `extern "C"` 让 C++ 调用者按 C 的方式链接这些接口，而 `#ifdef __cplusplus` 让同一个头文件也能被 C 编译器读取。[官方编译流程](https://docs.arduino.cc/arduino-cli/sketch-build-process/)

`.c/.cpp` 不会像 `.ino` 一样自动补充 `Arduino.h`，需要 Arduino 接口时自行包含。头文件若用到 `uint8_t` 等类型，也应自行包含 `<stdint.h>`，保证可以独立使用。

## 5. 统一初始化与依赖约定

目前 `Initial.h` 汇总了 `Arduino.h` 和 LED 头文件，因此主程序通过它也能看到 LED 接口。新增功能时，建议使用该功能的源文件直接包含对应头文件，让依赖关系清楚可见。

新增需要初始化的模块后，在 `Initial.c` 中添加对应头文件和调用。以下是**实现上述 Key、Control 模块之后**的扩展示例：

```c
#include "Initial.h"
#include "src/Hardware/LED.h"
#include "src/Hardware/Key.h"
#include "src/Software/Control.h"

void Initial_All(void)
{
    LED_Init();
    Key_Init();
    Control_Init();
}
```

先初始化被依赖的模块，再初始化使用它的上层模块。建议各实现文件包含自己的头文件，`Initial.c` 也遵循这一约定；以上是扩展示例，本文没有修改当前源码。

在 `Template.ino` 中接入持续运行逻辑：

```cpp
#include "Initial.h"
#include "src/Software/Control.h"

void setup()
{
    Initial_All();
}

void loop()
{
    Control_Run();
}
```

底层模块只包含自身需要的头文件，不反向包含 `Initial.h`。推荐的依赖方向为：主程序和初始化入口调用各模块，软件层调用硬件层，硬件层调用芯片或 Arduino 接口。无需为了添加模块，把所有头文件都塞进 `Initial.h`。

### 什么时候使用 .cpp

调用 `WiFi.begin()`、`Serial.println()`，或使用 `String`、类等 C++ 功能时，将实现写为 `.cpp`，并包含所需头文件。`Wifi_Base` 以后接入 Arduino Wi-Fi 库时通常采用这种方式。

`extern "C"` 只规定函数接口的链接方式，不能让 `.c` 编译器识别 C++ 语法。可以用 C 风格函数作为对外接口，在 `.cpp` 内部调用 C++ 库。由于当前初始化入口是 `Initial.c`，不要把含有 C++ 类声明的头文件直接汇总进它会包含的 `Initial.h`；让 C++ 依赖留在对应 `.cpp` 内部。

## 6. 常见问题与项目交付

| 现象 | 优先检查 |
|---|---|
| `No such file or directory` | 从当前文件所在目录计算相对路径，检查目标是否存在及大小写是否一致。 |
| `undefined reference` | 函数是否有实现、声明和定义是否一致、源码是否位于根目录或 `src` 下、C 接口是否有正确的链接声明。 |
| `multiple definition` | 是否包含了 `.c/.cpp`，或搬移函数后仍保留旧定义；普通函数实现放在源文件中。 |
| 出现类、`String`、`Serial` 等相关编译错误 | 是否误用 `.c` 编译 C++ 代码，是否包含了所需头文件。 |
| 编译成功但功能没执行 | 是否调用初始化或运行函数，再检查引脚、接线和模块状态。 |
| 编辑器没有报错，但实际编译失败 | 编辑器提示与真实编译是两套机制，以编译日志为准。 |

交付时保留整个 `Template` 源码目录结构，包括主程序、初始化文件、`src` 和本说明。当前空的 `Wifi_Base` 只是预留目录；Git 默认不保存空目录，接收者没有看到它时可按需新建。

接手者需要安装对应开发板支持和外部依赖，核对开发板选项及串口配置后重新编译。当前项目选择的是 XIAO ESP32S3；`.vscode` 中可能包含本机路径和串口，需要按实际环境核对。`build` 是生成产物，可以重新生成，不要在其中修改源码。

官方参考：[Arduino 工程目录规范](https://docs.arduino.cc/arduino-cli/sketch-specification/)、[Arduino 编译与链接流程](https://docs.arduino.cc/arduino-cli/sketch-build-process/)。

## 7. 全局 FreeRTOS 任务状态监视

接口声明在 `Initial.h`，实现在 `Initial.c`，C 和 C++ 文件均可调用：

```c
void print_FreeRtos_Task(void);
```

### 原理与配置

1. 用 `uxTaskGetNumberOfTasks()` 查询任务数量，动态分配快照数组，额外预留 4 个元素。
2. 用 `uxTaskGetSystemState()` 获取全局任务状态；若任务数增长导致容量不足，最多尝试 3 次。
3. `vTaskDelay(pdMS_TO_TICKS(1000))` 阻塞调用任务约 1 秒，其他任务继续被调度。
4. 再获取一次快照，通过任务编号和句柄匹配前后任务，用运行计数差计算这段采样窗口的 CPU 占用。
5. 打印第二次快照中的任务列表，释放两份快照占用的堆内存。

当前 XIAO ESP32S3 / Arduino ESP32 3.3.11 构建配置已启用：

```text
CONFIG_FREERTOS_USE_TRACE_FACILITY=y
CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y
CONFIG_FREERTOS_VTASKLIST_INCLUDE_COREID=y
CONFIG_FREERTOS_RUN_TIME_STATS_USING_ESP_TIMER=y
```

直接调用 `uxTaskGetSystemState()` 不要求开启格式化统计函数。若换用未启用前两项的 SDK，函数会打印配置提示；只在草图中重新定义宏不能补上预编译内核缺失的功能。

### 当前调用方式

```cpp
#include "Initial.h"

void setup()
{
    Initial_All();
}

void loop()
{
    print_FreeRtos_Task();            // 内部采样约 1 秒
    vTaskDelay(pdMS_TO_TICKS(2000));  // 两次报告间再等待 2 秒
}
```

约每 3 秒输出一张表，打印耗时和调度延迟会让周期稍长。函数本身不创建后台任务，也不负责串口初始化。后续 `loop()` 接入需要及时执行的业务时，应把此调用移入独立的低优先级监视任务。

### 输出字段

| 字段 | 含义 |
|---|---|
| ID / Task | 任务编号 / 任务名称，包含应用任务和系统任务 |
| Pri / Base | 当前优先级 / 基础优先级；持有互斥锁时可能因优先级继承而不同 |
| State | 第二次快照时的 Running、Ready、Blocked、Suspended、Deleted 等状态 |
| Affinity | 核亲和性：0、1 或 ANY；不是这一时刻实际运行在哪个核心 |
| StackMin(B) | 任务创建以来最小剩余栈，单位字节；不是已使用栈，不乘 4 |
| RunTime(cnt) | 第二次快照的累计运行计数；当前使用微秒时钟和 32 位计数，会回绕 |
| CPU% | 两次采样间的运行计数差 / 总计数差 × 100%；100% 表示占满一个核心 |

双核的所有任务（包含 Idle）占用之和可能接近 200%，不要当作整颗芯片的 0～100% 利用率。CPU% 是调试估计：计数在任务切换时结算，采样本身也有开销，不能替代严格实时分析。

`NEW` 表示该任务只在第二次快照出现（或句柄被新任务复用），没有同一任务的基线；`N/A` 表示采样间隔为零或运行计数尚未合理结算。函数采用无符号差值处理短窗口内的单次计数器回绕。采样期间已经删除的任务可能不出现在最终列表中。

### 控制台与使用限制

- 使用 C 的 `printf()` 输出到 ESP-IDF 调试控制台，而不是直接调用 Arduino `Serial` 对象。当前 SDK 主控制台是 UART0、115200 波特率，并启用了 USB Serial/JTAG 辅助控制台；若更改 USB 模式或控制台配置，应相应选择串口监视端口。
- 由一个普通任务低频调用；不要在 ISR、临界区、软件定时器回调或持有业务互斥锁时调用。
- 任务名称由 FreeRTOS 任务本身持有，`TaskStatus_t` 只保存指针。打印期间不要并发删除被监视的任务；需要动态删除时，在应用层协调任务生命周期与监视操作。
- 快照采集和串口打印都有开销。此功能用于开发调试，正常业务应自行决定是否保留周期输出。

参考：[ESP-IDF FreeRTOS API](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32s3/api-reference/system/freertos_idf.html)。
